# 남은 지연의 연결 단계 분리 (#41)

2026-10-24. #41을 다시 열고 PR #42 뒤 남은6초대 전체 왕복을 재분석한다. 앱/DB 처리는 빨라졌으나 전체 왕복까지 해결됐다고 완료 처리한 것은 성급했다.

## 직접 관측

동일한 무쿠키 GET /api/auth/me는401·Server-Timing app0.3ms·db0회였다. curl의 누적 시간은 DNS0.031ms, TCP연결0.275ms, TLS완료7.789초, 첫바이트8.184초였다.

추가 verbose 타임스탬프(경과 차이만 해석):

- 프록시 CONNECT 전송: 02:49:16.276796
- 프록시 HTTP200 응답/터널 준비: 02:49:24.063664~063710
- TLS ClientHello: 02:49:24.066090
- TLS ServerHello: 02:49:24.067001
- TLS 연결 완료: 02:49:24.068110
- 실제 GET 전송: 02:49:24.068593
- 원격 HTTP401 첫 헤더: 02:49:24.432338

약7.787초가 CONNECT 응답 대기에서 발생했고, 터널 준비 뒤 TLS 자체는 수ms, 실제 HTTP GET 이후 응답은 약364ms였다. 이 관측의 다초 지연은 HTTP 요청이 앱에 도착하기 전의 검증 환경 프록시 터널 준비 구간이다. 앱 콜드 스타트·SQL 실행으로 설명하지 않는다. 프록시 내부의 정책/승인/연결 처리 중 어느 동작인지는 이 데이터만으로 확정하지 않는다. 일반 이용자의 네트워크에도 같은 지연이 있다고 확대하지 않는다.

## 독립 비교

scripts/measure-public-latency.mjs는 고정된 운영 주소의 /api/auth/me(무쿠키401)·/login(200)을 각각3회 조회하고 DNS/TCP/TLS/첫바이트/전체 누적 시간과 Server-Timing을 기록한다. 세션·쿠키·PIN·비밀값은 사용하지 않으며 프록시 주소/인증 정보도 출력하지 않는다. 임시 헤더 파일은 실행 후 제거한다.

별도 GitHub Actions runner에서 같은 스크립트를 실행해 검증 환경의 프록시 경로와 비교한다. workflow는 수동 및 해당 진단 파일 PR에서만 실행하며 계정/DB 변경이나 배포 작업을 하지 않는다. 독립 실행 결과와 최종 판단은 PR에 기록한다. 현재의 직접 관측과 독립 비교 성공 여부를 구분한다.
