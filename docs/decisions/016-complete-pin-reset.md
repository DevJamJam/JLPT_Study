# 초기 PIN 강제 변경 완료 (#35)

2026-10-23. 제한 세션의 POST /api/auth/complete-reset과 새 PIN·확인 폼을 연결한다. 승인된 로그인/가입 화면의 CSS Modules·토큰·공통 Button·PIN 검증·HTTP/쿠키 처리를 재사용한다.

- 세션은 요청 쿠키에서만 도출하고 사용자 ID를 body로 받지 않는다. 새 PIN과 확인이 ASCII4자리로 일치해야 한다. 제한 세션만 사용하며 현재와 동일한 PIN은 PIN_UNCHANGED로 거부한다. 초기값0000에서 실제 다른 값으로 변경하기 위한 제약이며1111·1234 같은 동일/연속 숫자를 일반적으로 금지하는 정책은 아니다.
- 기존 인증 시도 예약을 reserveUserAttempt로 공유한다. 사용자 닉네임·신뢰 출처를 같은 HMAC namespace로 묶고 change_pin 예산 예약 후 현재 자격증명 확인·scrypt를 수행한다. 429는 해시/변경 전에 반환한다.
- complete_pin_reset은 그룹→멤버→자격증명→현재 세션을 잠그고 만료·현재 버전·제한 모드를 재확인한다. 새 해시 저장·버전 증가·전 세션 폐기·현재 기기 정상 세션 발급을 하나의 트랜잭션으로 처리한다. 재전송·동시 요청은 이전 세션을 재사용할 수 없다. 새 세션 생성 실패 시 모두 롤백한다.
- SQL은 SECURITY INVOKER·빈 search_path, RPC EXECUTE는 service_role만 허용한다. CLI migration new로 파일을 생성하고 Supabase에 jlpt_complete_pin_reset 이름으로 적용했다. 테이블·기존 계정·관리자 상태는 변경하지 않는다.
- 응답은 공개 profile과 새 HttpOnly 보안 쿠키뿐이다. PIN·세션 원문·DB 오류 원문을 JSON/로그에 넣지 않는다. 401은 사용자 쿠키를 제거한다. 응답 유실로 이미 변경됐을 수 있으므로 만료/처리 완료 상태는 새 PIN으로 재로그인을 안내하고 자동 재전송하지 않는다.
- 실패 시 폼 입력을 유지한다. 성공하면 제한 폼을 없애고 me로 새 정상 세션을 확인한다. 변경 중 폼과 로그아웃을 비활성화하며 로그아웃 문구는 변경하지 않는다. PIN을 웹 스토리지에 저장하지 않는다.

## 실제 검증

npm run check/build·단위58개 통과. 전체 브라우저45개 통과 후 대기 상태·버튼 간격 수정에 대해 새 흐름6개를 다시 통과했다. 375×667·820×1180·1280×900에서 실제 빈 입력 화면을 캡처했다. 브라우저 검사는 API 응답을 대체하고 실제 폼·fetch·라우트를 실행한다.

Supabase 계약: 정상 변경·버전 증가·전 세션 폐기·정상30일 세션·다른 사용자 보존·일반 세션 거부·버전 불일치·만료·재전송 거부·새 세션 충돌 시 전체 롤백을 검증하고 테스트 데이터를 롤백했다(테스트 그룹0개 확인). 동시 요청은 격리 PostgreSQL CI에서 두 번째 변경 UNAUTHORIZED·버전2·새 세션1개를 검사한다. 보안 advisor는 기존 INFO15건이며 WARN/ERROR는 없다. https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy

첫 DB 적용 도구 응답은 Invalid or expired requestState였다. 함수 미존재를 조회해 미적용을 확인한 뒤 재적용에 성공했다. 새 화면 검사에서 PIN 변경 대기 상태를 로그아웃과 공유해 문구가 바뀌는 문제를 발견하고 상태를 분리했다.

운영 API 및 운영 실제 브라우저 통합은 병합 후 별도 검증 결과로 기록한다. 기존 운영 브라우저 검사 환경의 프록시 인증서 오류는 해결됐다고 주장하지 않는다. 일반 PIN 변경·프로필 설정 팝업·관리자 초기화 실행·기록/통계는 후속이다.
