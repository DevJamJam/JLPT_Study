# 026 — 내 기록 수정·삭제 화면

## 문제와 선택

월별 내 기록은 생성·조회만 제공했다. 기존 RecordForm에 편집 모드를 추가하고
기존 Button·StudyDialog·SweetAlert2를 재사용한다. 새 서버 경로나 DB 스키마는 없다.

- 본인 목록의 수정은 날짜·종류·시간·시작시각·공부량·단위·메모를 기존 값으로 채운다.
- PATCH는 조회한 원래 version과 expectedUserId를 함께 보낸다. 다른 탭의 계정 변경을
  감지하면 재전송을 막고 다시 로그인하도록 안내한다. 성공 후 대상 월로 이동·목록 무효화·토스트.
- 실패는 입력을 유지한다. 응답 유실은 같은 입력·version을 유지해 재시도한다.
  GET으로 결과를 확인해도 편집을 자동 성공으로 간주하지 않고 현재값 검토 단계로 전환한다.
- CONFLICT는 초안을 유지하고 저장을 차단한다. 최신 기록 요약을 표시하며, 불러오기는
  초안 폐기 확인 후 GET으로 다시 읽는다. 그 뒤 새 version을 기준으로 사용자가 다시 저장한다.
- 삭제는 별도 확인 팝업에서 선택 기록을 보여주고 SweetAlert2 영구삭제 경고를 확인해야 요청한다.
  실패는 같은 ID·version으로 재시도한다. 충돌은 자동 삭제하지 않고 최신 기록 확인 및 재확인이 필요하다.
- 저장·삭제 중 닫기/Escape·중복 제출을 차단한다. 수정의 브라우저 종료는 beforeunload 기본 안내만 제공하며
  초안 복원은 보장하지 않는다. 서버 데이터는 메모리 Query 캐시만 사용한다.
- 성공 토스트는 팝업 해제 후 표시한다. 삭제 후 현재 월 유지·목록 갱신, 마지막 기록이면 빈 상태를 표시한다.
- 확인창 공통 내부 함수를 추출해 기존 초안 폐기 동작을 유지한다. 사용자 문자열은 text/titleText로 전달한다.

## 검증

기존 단위87개, format/lint/typecheck·운영 빌드 통과 후 브라우저 검사를 추가한다.
신규6개 흐름을 SE3·패드·PC에서 실행해 기존78개와 합계96개를 검증한다.
최초 CI #67에서 단위87·브라우저96·실제 DB 통합5 및 SQL 계약이 통과했다.
삭제 확인 캡처가 애니메이션 중 촬영되어 흐릿함을 발견했다. 확인창 애니메이션 완료를 기다린 뒤
촬영하도록 보완하며, 최종 head의 결과와 캡처는 PR에 기록한다.

## 한계

캡처와 브라우저 검사는 가상 API 데이터를 사용한 Chromium이다. 실제 iPhone Safari·운영 사용자
기록 수정·삭제·기기 간 동기화 검증은 포함하지 않는다. 팝업 URL/history 및 달력 상세 연결은
기존과 동일하게 후속 통합 작업이며 이번에는 월별 내 기록 화면의 직접 편집·삭제만 연결한다.
