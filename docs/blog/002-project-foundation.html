002 · 협업 기반과 설계를 먼저 저장한 이유

2026-10-07 · chore: 협업 규칙과 확정 설계 초기화

문제

새 레포는 비어 있었다. 설계와 협업 규칙을 코드와 함께 보관해야 이후 변경 이유를 확인할 수 있다.

이번에 만든 것

README, 작업 규칙, AGENTS.md, 이슈·PR 템플릿, 확정 설계, 컬러 토큰, 디자인 시안을 저장했다. 이 글도 같은 커밋에 포함한다.

왜 브랜치를 나누는가

main은 검증한 코드의 기준이고, 작업 브랜치는 한 기능을 만드는 자리다. 개인 프로젝트에서는 develop을 생략해 관리 부담을 줄인다. PR은 작업을 함께 확인하는 요청서다.

핵심 구조

docs/blog/002-project-foundation.html처럼 글을 순번으로 보관한다. 같은 커밋에 글과 변경 파일이 들어 있으므로 Git 이력으로 서로 연결할 수 있다. 글에 자기 커밋 해시를 쓰면 파일과 해시가 다시 바뀌므로 해시는 커밋 후 보고한다.

공개 문서 정리

디자인 출처에 관한 불필요한 설명을 삭제하고 시안 닉네임을 가상 사용자로 바꿨다. 화면 장식은 선택 이모지와 CSS를 사용한다.

검증과 한계

HTML 파싱, 상대 링크 존재, 시안 JavaScript 문법을 검사한다. 완료 여부는 함께 전달하는 실제 검사 결과를 따른다. 앱·DB·빌드는 미구현이고 실기기 검증은 하지 않았다. 개인 계정 앱 설치 후 이슈 #1 생성이 성공했다. 이 작업은 chore/1-project-foundation 브랜치에서 진행한다. 이전 로컬 준비 커밋과 GitHub 커밋은 구분한다.
